# Caveworkers company production release

Caveworkers is deployed as a multi-tenant company control plane with **exactly four employee agents**: Data Analyst, Cybersecurity Analyst, Full Stack Backend Developer, and Software QA/Automation Engineer. The public application remains the only company-facing interface. Hermes is an internal execution runtime, never a customer dashboard, CLI, browser surface, or direct employee endpoint.

> **Release rule:** A company-facing deployment may run the four employee workspaces immediately, but Hermes-backed execution stays disabled until the private services pass the staged readiness checks below. No result may be represented as a completed tool action without an audit record from Caveworkers.

## No-new-billing release path

The existing managed Caveworkers publishing path may be used now for a controlled public candidate without activating a new Google Cloud billing account. This release keeps `HERMES_ENABLED=false`, retains fail-closed payment and connector behavior when their managed secrets are absent, and runs only the existing safe company workspaces, plans, approvals, tenant isolation, and deterministic fallback behavior. It is suitable for demonstrating the company control plane and onboarding a tightly managed pilot only after the acceptance checks below are completed.

This path does **not** substitute for the three-service Cloud Run topology. It cannot claim private Hermes tool execution, Secret Manager-backed production configuration, live payment processing, tenant Google connector OAuth, durable always-on queue processing, or a horizontally scalable realtime service unless those capabilities are configured and verified in the managed host. The user-facing result must accurately identify an unavailable provider or runtime as unavailable rather than simulate a result.

## Service topology

| Service | Exposure | Responsibility | Secrets it may receive |
|---|---|---|---|
| `caveworkers` | Public HTTPS Cloud Run service | Authentication, company tenancy, Firestore records, queue, approval records, Razorpay owner checkout, SSE workroom, token minting, and output redaction | Application, Firebase, payment, connector, model, and capability-signing secrets required by Caveworkers only |
| `caveworkers-hermes-bridge` | Cloud Run internal ingress only | Narrow MCP bridge for task context, approved employee memory, persisted draft artifacts, and approval requests | Bridge bearer and capability-signing key only, plus its dedicated Firestore identity |
| `caveworkers-hermes` | Internal Cloud Run service with IAM invocation | Hermes Runs API with one bridge-only MCP allow-list | Hermes API bearer, OpenRouter key, bridge URL, and bridge bearer only |

The public service begins with `HERMES_ENABLED=false`. Its controlled deployment script caps Cloud Run at one continuously allocated instance because the current workroom SSE connections, presence, and request-rate windows are process-local. Firestore already provides the durable task, approval, memory, audit, and queue records, but horizontal scale must wait for a shared realtime fan-out and rate-limit service.

## Employee execution contract

| Employee | Private runtime skills | Initially usable bridge intents | Explicitly unavailable without a later adapter and approval design |
|---|---|---|---|
| Data Analyst | KPI analysis, SQL analysis, anomaly detection, business reporting | Read bounded task context and memory; persist a reviewable draft artifact | Database writes, messages, payment activity, external publishing |
| Cybersecurity Analyst | Defensive log, dependency, configuration, and incident analysis | Read bounded task context and memory; persist a defensive draft artifact | Scanning, exploitation, identity changes, credential handling, production changes |
| Full Stack Backend Developer | Repository analysis, debugging, API design, migration planning, code review | Read bounded task context and memory; persist an implementation draft | Repository writes, merge, migration, deployment, secret changes |
| Software QA/Automation Engineer | Test strategy, regression analysis, API testing, defect analysis | Read bounded task context and memory; persist a test-plan draft | Personal-browser control, shared-environment mutation, production testing; sandbox requests need manager approval |

Every bridge call requires a short-lived, single-use capability generated by Caveworkers. The token binds the company, employee, task, exact intent, expiry, and nonce. A static MCP bearer is transport authentication only; it does not authorize tenant data. Capability tokens are redacted from outputs and cannot be reused.

## Operator release sequence

First, rotate any credentials that were previously exposed and create managed Secret Manager versions. Use the repository’s [`SECURITY_ROTATION.md`](../SECURITY_ROTATION.md) procedure. Give the public Caveworkers service account Firestore access, narrowly scoped Secret Manager access, and `roles/run.invoker` only for the private Hermes service. Give the bridge its own service account with only the required Firestore collections and the bridge secrets. The Hermes runtime must not receive Firebase Admin, Razorpay, Google OAuth, tenant connector, Gmail, or capability-signing credentials.

Next, create the `caveworkers` Artifact Registry repository, submit the three Cloud Build definitions, and deploy the public service with [`deploy-caveworkers.sh`](../deploy-caveworkers.sh). Set the actual public HTTPS address as both `PUBLIC_APP_URL` and the appropriate `ALLOWED_ORIGINS` entry. Configure that host in Firebase Authentication, the Google OAuth redirect client, and Razorpay’s webhook configuration. Deploy Firestore rules from `firebase.json` before allowing customer sign-in.

After the public service has passed its application checks, deploy the internal capability bridge using [`hermes-bridge/deploy-capability-bridge.sh`](../hermes-bridge/deploy-capability-bridge.sh). Deploy the authenticated Hermes service with [`hermes-runtime/deploy-private-runtime.sh`](../hermes-runtime/deploy-private-runtime.sh). Confirm that the Hermes API capability response includes Runs submission, status, events, stop, and approval; confirm its toolset endpoint contains only `mcp-caveworkers-bridge`; and confirm that the bridge health endpoint is reachable only through the internal network.

## Staged Hermes enablement

The first live runtime test must use a non-production company test tenant and the Data Analyst only. Submit a bounded analysis request that reads task context and creates a draft artifact. Verify the tenant-scoped artifact, task record, audit record, and absence of a payment or external-action event. Then exercise cancellation, a deliberately failed capability, a replayed nonce, and a manager approval pause. Do not enable a second employee until every expected result is visible in the correct tenant’s records and no data appears in another tenant.

Only after the staging evidence is reviewed should the operator set `HERMES_ENABLED=true` on the public service for the selected pilot tenant. Enable additional companies progressively. The Data Analyst, Cybersecurity Analyst, Backend Developer, and QA Engineer must remain within their contracts above; higher-risk repository, migration, deployment, connector-write, browser, or real test-run adapters require their own implementation, evidence, rollback plan, and approval gate.

## Company acceptance gate

| Area | Required evidence before inviting customers |
|---|---|
| Identity and tenancy | Firebase Google sign-in, logout, session revocation, company membership isolation, CSRF rejection, and cross-tenant API denial |
| Payments | Live-mode Razorpay order and signature validation in the intended account, valid webhook delivery, duplicate-webhook handling, invalid-signature rejection, reconciliation owner, and refund process |
| Durability | Firestore backups, documented restore exercise, retention/deletion export check, and queue recovery check |
| Employee workrooms | One task for each of the four employees with an approved plan, isolated history and memory, and an auditable result or safe fallback |
| Private runtime | Internal-only bridge, authenticated Hermes service, bridge-only toolset, Data Analyst draft-artifact smoke test, cancellation, approval pause, nonce replay denial, and output-token redaction |
| Operations | `/api/health` monitoring, error monitoring, alert routing, named incident owner, support inbox, scheduler tick, structured logs, and release rollback owner |

The repository CI gate remains `npm ci`, `npm run lint`, `npm test`, `npm run build`, and `git diff --check`. Real Firebase, Razorpay, OAuth, Cloud Run, Firestore restore, and Hermes smoke tests are acceptance tests performed in the operator’s staging or production account, not with mocked CI credentials.

## Scale and change-management boundary

The controlled initial production configuration is company-ready for a managed low-volume launch with one public worker instance. It is not a claim that the current process-local realtime layer is horizontally scalable. Before raising `max-instances` above one, move rate limiting, employee presence, SSE event fan-out, and remaining cache state to shared managed services; add queue lease metrics, dead-letter operations, and retry backoff observability. Release these changes through a staging environment, not directly against customer tenants.
